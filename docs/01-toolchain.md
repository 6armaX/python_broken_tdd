# 01. Шпаргалка по инструментам

Все команды запускаются через `uv run`, то есть внутри `.venv` проекта.

## Команды одной строкой

| Задача                       | Команда                                                     |
| ---------------------------- | ----------------------------------------------------------- |
| Прогнать всё как в CI        | `./scripts/check.sh`                                         |
| Только часть 1               | `./scripts/check-part1.sh`                                   |
| Только часть 2               | `./scripts/check-part2.sh`                                   |
| Проверить окружение          | `./scripts/doctor.sh`                                        |
| Форматирование «как надо»    | `uv run ruff format .`                                       |
| Проверка форматирования      | `uv run ruff format --check .`                               |
| Показать, что именно изменит форматтер | `uv run ruff format --check --diff .`             |
| Линт                         | `uv run ruff check .`                                        |
| Линт + автоисправление       | `uv run ruff check --fix .`                                  |
| Типы                         | `uv run mypy src tests`                                      |
| Все тесты                    | `uv run pytest`                                              |
| Только тесты части 1         | `uv run pytest tests/test_money.py tests/test_inventory.py tests/test_reporting.py` |
| Один тест                    | `uv run pytest tests/test_inventory.py -k low_stock`         |
| Остановиться на первой ошибке| `uv run pytest -x`                                           |
| Покрытие расчёта заказа      | `uv run pytest tests/test_checkout.py --cov=shop.checkout --cov-report=term-missing` |

## ruff format — форматтер

Форматтер не решает, как код должен выглядеть, он приводит уже принятые решения
к единому виду: отступы, кавычки, переносы длинных строк, порядок импортов,
пустые строки, завершающий перевод строки.

* `uv run ruff format --check .` — только проверить (это делает CI).
* `uv run ruff format .` — переписать файлы.
* `uv run ruff format --check --diff .` — показать, что именно изменится.

Правило: если CI ругается на форматирование — запускайте `ruff format`, а не
правите руками. Руками выйдет иначе, чем у форматтера, и проверка снова упадёт.

Настройки лежат в `pyproject.toml`, секция `[tool.ruff]`: `line-length = 100`,
`quote-style = "double"`, `target-version = "py312"`.

Форматтер проверяет и Python-блоки внутри файлов `.md`: примеры кода в
документации тоже должны быть отформатированы, иначе джоба `format` упадёт.

## ruff check — линтер

Линтер ищет ошибки, которые компилятор пропускает. Включённые наборы правил:
`E` (pycodestyle), `W` (warnings), `F` (Pyflakes), `I` (isort), `N` (naming),
`UP` (pyupgrade), `B` (bugbear), `SIM` (simplify), `C4` (comprehensions),
`RET` (return), `C90` (сложность).

Частые коды, которые встретятся в части 1:

| Код     | Что означает                                                   | Что делать                        |
| ------- | -------------------------------------------------------------- | --------------------------------- |
| `F401`  | импорт не используется                                          | удалить импорт                    |
| `F541`  | f-строка без подстановок                                        | убрать лишний `f`                 |
| `F841`  | переменная присвоена и не используется                          | удалить или использовать          |
| `I001`  | блок импортов не отсортирован                                   | `uv run ruff check --fix .`       |
| `E711`  | сравнение с `None` через `==`                                   | писать `is None`                  |
| `B006`  | изменяемый объект в аргументе по умолчанию                      | заменить на `None` и создавать внутри |
| `RET505`| `else` после `return`                                           | убрать `else`, выровнять ветки    |
| `C901`  | функция слишком сложна (порог 9 в `pyproject.toml`)             | разбить на помощники или выпрямить ветвление |

`C901` в части 1 не встречается — там нет функции с таким числом ветвлений. В части 2
он появится, как только все правила валидации окажутся в одной функции. Это подсказка
разбить её на помощников, а не повод поднять порог в `pyproject.toml`.

`--fix` чинит безопасные случаи автоматически (сортировку импортов, лишние
импорты, `== None`), остальное придётся исправить самому. Никогда не добавляйте
`# noqa: <код>` вместо починки: это отключает проверку навсегда и прячет
следующую настоящую ошибку за той же строкой.

## mypy — проверка типов

Проект запускает mypy в строгом режиме (`strict = true` в `pyproject.toml`).
Это значит: у всех функций должны быть аннотации, включая тестовые.

```bash
uv run mypy src tests
```

| Код                 | Что означает                                        | Как чинить                                       |
| ------------------- | ---------------------------------------------------- | ------------------------------------------------ |
| `no-untyped-def`    | у функции нет аннотаций                              | дописать типы                                    |
| `no-untyped-call`   | вызов функции без аннотаций из типизированного кода   | дописать типы в callee                           |
| `return-value`      | возвращается не тот тип, что обещано                 | привести значение к обещанному типу               |
| `arg-type`          | аргумент другого типа                                 | исправить тип или привести значение              |
| `operator`          | операция невозможна для этих типов                    | скорее всего, аннотация врёт: проверьте её        |

Аннотация — это обещание. Если написано `total_value: str = ""`, а дальше
складываются `int`, mypy прав: обещание нарушено, и в коде окажется строка там,
где ожидалось число.

## pytest — тесты

```bash
uv run pytest -v                      # подробно, по одному тесту на строку
uv run pytest tests/test_inventory.py # один файл
uv run pytest -k promo                # тесты, в имени которых есть promo
uv run pytest -x                      # остановиться на первом падении
uv run pytest --tb=long               # полный трейсбек
```

Как читать падение:

```text
E       AssertionError: assert 18905 == 12_000
```

Слева — то, что вернула функция, справа — то, что ожидал тест. Разница в первых
цифрах обычно указывает на место ошибки в порядке операций.

Важная особенность проекта: в `pyproject.toml` включено `filterwarnings = ["error"]`,
то есть **любое предупреждение Python превращается в ошибку**. Если тест падает с
`DeprecationWarning`, это сигнал: вызывается устаревшая функция, которую пора
заменить.

## Покрытие

```bash
uv run pytest tests/test_checkout.py --cov=shop.checkout --cov-report=term-missing
```

`term-missing` показывает номера строк, которые не выполнились ни одним тестом.
В CI требуется не ниже 90 % (`--cov-fail-under=90`): непокрытая ветка почти всегда
означает непроверенное правило из ТЗ.

## Данные без классов

Проект не использует классы, поэтому структуры данных — словари и списки:

```python
lines: list[dict[str, str]] = [{"sku": "SKU-1", "qty": "2", "unit_price_kopecks": "1990"}]
```

* `list[dict[str, str]]` — список словарей, у каждого строковые значения.
* Значение достаётся по ключу: `line["qty"]`.
* Чтобы получить число: `int(line["qty"])`.

Почему строки: данные приходят из складской выгрузки, и на границе их удобно
проверять целиком, не разбирая типы. Такой словарь можно прочитать глазами прямо
в тесте, и mypy при этом знает, что все значения — строки.

## Ошибки без исключений

В проекте нет `try` / `except` и `raise`. Некорректный вход — это обычное
возвращаемое значение:

```python
def validate_order(lines: list[dict[str, str]]) -> str | None:
    if not lines:
        return "заказ не содержит позиций"
    return None
```

Проверка в тесте:

```python
assert validate_order([{"sku": "SKU-1", "qty": "1", "unit_price_kopecks": "100"}]) is None
assert validate_order([]) is not None
```

Обратите внимание на `is None`, а не на `== None` — за это ругается линтер.

## Немного git

```bash
git status               # что изменилось
git diff                 # подробно, что именно изменилось
git diff --staged        # то же, но по проиндексированному
git log --oneline        # история коммитов
git add -A && git commit -m "test: проверка границы порога"
```

Для части 2 порядок коммитов значим: сначала коммит с тестом, потом — с кодом.
Это проверяет `./scripts/check-part2.sh` и джоба `tdd-history` в CI.
