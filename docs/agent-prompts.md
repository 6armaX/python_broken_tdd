# Промпты для агента

Все промпты начинаются с чтения `AGENTS.md` и ТЗ. Дайте агенту ровно один
красный тест и попросите сделать зелёным именно его.

## Шаг 0. Подготовка

```text
Работаем в репозитории shop-broken-tdd (учебный проект).

1. Прочитай AGENTS.md в корне репозитория и соблюдай эти правила.
2. Прочитай src/shop/specs/checkout.md — это требования к расчёту суммы заказа.
3. Прочитай tests/test_money.py, чтобы понять стиль тестов этого проекта.
4. Выполни ./scripts/setup.sh, если ещё не выполнял.
```

## Шаг 1. Реализовать один красный тест

```text
Задача: сделать зелёным ровно один тест — tests/test_checkout.py::test_empty_order_is_rejected

Что нужно: реализовать тело функции validate_order в src/shop/checkout.py так,
чтобы тест проходил.

Ограничения:
- не изменяй ни один файл в tests/;
- не трогай остальные тесты, даже если они падают;
- не добавляй классы, try/except и raise;
- не добавляй зависимости и не меняй pyproject.toml;
- сделай минимально необходимый объём изменений.

Готово считается, когда:
  uv run pytest tests/test_checkout.py::test_empty_order_is_rejected
проходит, а остальные тесты не изменились по сравнению с тем, что было до тебя.

В конце покажи вывод pytest и краткий diff.
```

## Шаг 2. Реализовать вычисление по одному тесту

```text
Задача: сделать зелёным тест tests/test_checkout.py::test_tier_discount_at_first_threshold

Контекст: calculate_order_total сейчас возвращает None для всего. Реализуй
минимальный расчёт, который делает этот тест зелёным: subtotal, ярусная скидка,
НДС — и ничего сверх того, что нужно тесту.

Ограничения те же: tests/ не трогать, ни одного класса и исключения,
константы из src/shop/checkout.py не менять.

Покажи вывод pytest и краткий diff.
```

## Шаг 3. Рефакторинг

```text
Задача: рефакторинг без изменения поведения.

Сейчас зелёные такие-то тесты: <перечислить>.
Выполни ./scripts/check-part2.sh и посмотри, где код можно упростить:
- убрать промежуточные переменные, которые не нужны;
- убрать дублирование между validate_order и calculate_order_total;
- назвать вещи понятно, а не abbr_.

Запрещено: менять тесты, менять публичные сигнатуры и константы,
ослаблять проверки.

После рефакторинга все тесты должны остаться зелёными. Покажи вывод.
```

## Шаг 4. Ревью чужого решения

Когда агент сделал всё сразу и вы хотите понять, что он наделал:

```text
Проведи ревью изменений относительно HEAD: git diff

Проверь по списку и ответь по пунктам:
1. Есть ли классы или try/except, которых быть не должно?
2. Не изменены ли тесты, константы и pyproject.toml?
3. Все ли ветки из src/shop/specs/checkout.md покрыты тестами?
4. Какие правила ТЗ агент, по-видимому, понял неправильно?
5. Какие граничные случаи не проверены тестами?

Ничего не правь сам, только список замечаний.
```

## Шаг 5. Проверка перед сдачей

```text
Выполни ./scripts/check.sh и покажи полный вывод.
Если что-то красное — скажи прямо, что именно и почему.
Не описывай невыполненную работу как выполненную.
```

## Как настроить агента на роль «исполнителя, а не судьи»

Главный риск: агент увидит красные тесты и решит, что проще сделать их зелёными
любой ценой. Помогают три вещи:

1. **Правила проекта в файле.** `AGENTS.md` агент перечитывает целиком, а не
   полагается на память о прошлых диалогах.
2. **Явный запрет в каждом промпте.** «не изменяй ни один файл в tests/»
   звучит глухо, зато работает.
3. **Машинная проверка.** `scripts/check_tdd_history.py` и запрет `skip` / `xfail`
   в джобе `tdd-history` ловят нарушение даже тогда, когда агент убедил вас, что
   «это была оптимизация».

## Чего не стоит от агента

Не стоит: писать тесты за вас, подбирать ожидаемые значения («посмотри, что
вернулась сумма 22686, и запиши её в тест»), выбирать архитектуру, решать, что
должно быть в `validate_order`.

Стоит: переводить намерение в код, находить граничные случаи **в коде**
(«у тебя деление на ноль, если qty = 0»), объяснять, почему реализация сложнее,
чем кажется, и честно говорить, когда не понял требование.
