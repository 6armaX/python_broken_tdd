# Часть 1. Починка красного CI

## Задача

Сборка репозитория красная с самого начала — так задумано. Четыре независимые
джобы GitHub Actions падают по разным причинам, и каждая требует своего
подхода к инструментам.

Ваша работа: сделать `./scripts/check-part1.sh` полностью зелёным, не меняя тесты
и не отключая проверки.

## Что красное

| Джоба              | Что проверяет                        | Инструмент                    |
| ------------------ | ------------------------------------ | ----------------------------- |
| `format`           | единый вид кода                      | `ruff format --check`         |
| `lint`             | вероятные ошибки                     | `ruff check`                  |
| `types`            | соответствие аннотациям              | `mypy src tests` (strict)     |
| `tests`            | поведение кода части 1               | `pytest`                      |
| `tests` (3.13)     | то же самое на второй версии Python | `pytest`                      |

Полный набор тестов, включая ещё не написанную часть 2, проверяет джоба `tests` в
`part2-ci.yml`.

Сломаны два модуля: `src/shop/inventory.py` и `src/shop/reporting.py`.
Файлы `src/shop/money.py` и `tests/test_money.py` — эталон: они зелёные и
задают стиль проекта.

## Порядок работы

Воспроизведите красное состояние и читайте вывод:

```bash
./scripts/check-part1.sh
```

Дальше — от дешёвого к дорогому.

### Шаг 1. Форматирование

```bash
uv run ruff format .
```

Это единственный шаг, где вывод можно не читать: решение принимает инструмент.

### Шаг 2. Линт

```bash
uv run ruff check .
uv run ruff check --fix .        # то, что чинится автоматически
```

Оставшиеся замечания разбирайте по кодам — таблица в
[01-toolchain.md](01-toolchain.md).

### Шаг 3. Типы

```bash
uv run mypy src tests
```

Читайте сообщения как текст: «Function is missing a type annotation» значит
«дописать аннотации», «Unsupported operand types for + ("str" and "int")»
значит «здесь аннотация обещает строку, а складываются числа».

### Шаг 4. Тесты

```bash
uv run pytest tests/test_money.py tests/test_inventory.py tests/test_reporting.py
```

Здесь важно не спешить с правками. Сначала прочитайте падение и сформулируйте,
что функция должна делать, потом сравните с тем, что она делает.

## Ловушка, ради которой задание и затевалось

`ruff check --fix` чинит не всё. Неиспользуемые импорты, порядок импортов и
лишний `else` после `return` он поправит молча, а вот `B006` — изменяемый
объект в аргументе по умолчанию — придётся починить руками, иначе состояние
продолжит быть общим между вызовами, а тест
`test_reserve_units_starts_from_an_empty_ledger` — падать.

Типичные неправильные починки, которые «проходят линтер»:

| Как починить | Почему неправильно |
| ------------ | ------------------ |
| убрать третий аргумент функции | тесты вызывают её с двумя аргументами — сломается вызов |
| оставить `reserved: dict = {}` и добавить `# noqa: B006` | проверка отключена, ошибка осталась |
| объявить `total_value: str`, а в конце вернуть `int(...)` | `format_kopecks` получит строку и упадёт |

Общий порядок всегда такой: **формат → линт → типы → тесты**. Не пытайтесь
прогнать всё разом: так вы не поймёте, какой инструмент на что ругался.

## Вторая ловушка: предупреждения

Тесты частично падают не на ассертах, а с `DeprecationWarning`. В проекте
включено `filterwarnings = ["error"]`: предупреждение считается ошибкой, потому
что устаревшая функция однажды исчезнет и сломает код на ровном месте. Правильный
ответ — заменить вызов на актуальный, а не отключить `filterwarnings`.

## Что можно и что нельзя

Можно и нужно:

* править `src/shop/inventory.py` и `src/shop/reporting.py`;
* добавлять аннотации типов;
* запускать `ruff format` и `ruff check --fix` — это штатные шаги, а не хитрости;
* менять `pyproject.toml`, **кроме** ослабления правил: не добавляйте `# noqa`,
  `# type: ignore`, не отключайте правила в `select` и не поднимайте пороги,
  чтобы ошибка исчезла из вывода.

Нельзя:

* менять содержимое `tests/` (ни строки) — иначе задание не засчитывается;
* «лечить» тесты ослаблением: удалить `assert`, поставить `skip`, изменить
  ожидаемое значение под фактический ответ;
* трогать `src/shop/money.py` — это эталон;
* удалять джобы из `.github/workflows/`.

## Критерий готовности

```bash
$ ./scripts/check-part1.sh
  успех  Форматирование (ruff format)
  успех  Линт (ruff check)
  успех  Типы (mypy)
  успех  Тесты (pytest, часть 1)

Все проверки зелёные.
```

И на GitHub вкладка Actions — все джобы `part1-ci.yml` зелёные.

`./scripts/check.sh` на этом этапе остаётся красным: он запускает ещё и проверки
части 2, а она ещё не сделана. Полностью зелёным он станет после части 2.

## Что отсюда взять для работы

1. Красную сборку можно воспроизвести локально в одну команду — это дешевле,
   чем смотреть в интерфейс GitHub.
2. Инструменты делятся на «решает за тебя» (форматтер, `--fix`) и «требует
   понимания» (типы, тесты). Смешивать их в один заход бессмысленно.
3. Автофикс может изменить поведение. Проверки нужны не для красоты, а чтобы
   поймать именно это.
4. `git diff` перед коммитом — способ увидеть, что вы случайно изменили.
