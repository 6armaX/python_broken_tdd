# Часть 2. TDD и LLM-агент

## Задача

Реализовать расчёт суммы заказа в `src/shop/checkout.py` по требованиям из
[`src/shop/specs/checkout.md`](../src/shop/specs/checkout.md). Сигнатуры и
константы уже заданы, тела двух функций — заглушки:

```python
def validate_order(
    lines: list[dict[str, str]],
    promo_code: str = "",
    shipping_city: str = "",
) -> str | None:
    """Return a human readable reason why the order is invalid, or None if it is fine."""
    ...


def calculate_order_total(
    lines: list[dict[str, str]],
    promo_code: str = "",
    shipping_city: str = "",
) -> int | None:
    """Return the order total in kopecks, or None if the order is invalid."""
    ...
```

## Кто что пишет

| Кто        | Что делает                                                        |
| ---------- | ----------------------------------------------------------------- |
| **Вы**     | читаете ТЗ, формулируете ожидания, пишете тест, решаете, что верно |
| **Агент**  | превращает ваш красный тест в зелёный минимальным кодом            |

Это не распределение «по лучшей экономии», а содержание навыка: тест — это
исполняемое утверждение о требовании, и написать его выгоднее и быстрее, чем
проверять, придумал ли агент те же требования. Агент хорош в переводе намерения
в код и плох в догадках о намерении.

## Цикл RED → GREEN → REFACTOR

Один подход — один коммит с тестом, один — с кодом.

### 1. RED: вы пишете тест

Возьмите **одно** правило из ТЗ. Например, «заказ без позиций отклоняется».
Допишите тело заготовки:

```python
def test_empty_order_is_rejected() -> None:
    """Spec 3, rule 1: an order without lines cannot be processed."""
    assert validate_order([]) is not None
```

Убедитесь, что тест красный, и закоммитьте **только тест**:

```bash
uv run pytest tests/test_checkout.py -k empty_order
git add tests/test_checkout.py
git commit -m "test: отказ при пустом заказе"
```

### 2. GREEN: агент пишет код

Дайте агенту задачу в форме «сделай зелёным вот этот один тест, остальные
трогать нельзя». Готовые формулировки — в
[agent-prompts.md](agent-prompts.md).

Пока агент работает, ничего в `tests/` не меняйте.

### 3. Проверка

```bash
./scripts/check-part2.sh
```

Тест стал зелёным, остальные — нет. Это нормально: цикл повторяется.

### 4. REFACTOR: вы (или агент, с вашего разрешения) упрощаете код

Только когда всё зелёное. Рефакторинг без красного рядом — это переписывание.
Сделайте отдельный коммит.

### Повторить 18 раз

В `tests/test_checkout.py` 19 заготовок, один тест уже написан. Остальные
закрывают правила валидации, ярусные скидки, промокоды, потолок скидки,
доставку и НДС.

## Как настроить агента

Любой агент, умеющий читать файлы и запускать команды. Подойдут opencode,
Claude Code, Codex CLI, Aider, Cursor.

1. Склонируйте репозиторий и выполните `./scripts/setup.sh`.
2. Скажите агенту прочитать `AGENTS.md` — там правила проекта: запрет классов,
   запрет исключений, запрет трогать тесты и ослаблять проверки.
3. Дайте путь к ТЗ: `src/shop/specs/checkout.md`.
4. Дайте один конкретный тест, который нужно сделать зелёным.

Если агент поддерживает файлы правил (`AGENTS.md`, `CLAUDE.md`), достаточно
сказать «прочитай AGENTS.md в корне репозитория».

## Анти-паттерны

Эти вещи ломают смысл упражнения:

| Что делает агент | Почему это плохо                                                    |
| ---------------- | ------------------------------------------------------------------- |
| правит тест, чтобы он прошёл | тест — это требование; «починил» значит «сменил требование» |
| пишет сразу 15 тестов подряд   | теряется проверка гипотезы: непонятно, какой тест что доказывает |
| переписывает функцию целиком    | не TDD: сначала минимальный код, потом остальное                  |
| добавляет `try` / `except`     | нарушает правила проекта                                           |
| заводит класс `OrderTotalCalculator` | нарушает правила проекта; функций достаточно               |
| добавляет `# type: ignore`     | замаскирует настоящую ошибку типов                                 |
| пишет тест `assert f() is not None` для всех случаев | не проверяет значения, а только факт отказа |

Отдельный сюжет — агент, который «помогает с покрытием» и добавляет тесты ради
процента покрытия. Формально джоба зелёная, смысла в тесте нет.

## Что проверяет CI

| Джоба              | Что требует                                                     |
| ------------------ | --------------------------------------------------------------- |
| `tests`            | весь набор зелёный (то есть часть 1 не сломана)                  |
| `checkout-coverage`| покрытие `shop.checkout` не ниже 90 %                            |
| `tdd-history`      | не меньше 10 тестов, в каждом есть `assert`, тесты закоммичены раньше кода |

Проверку порядка выполняет `scripts/check_tdd_history.py` — она смотрит на
историю git: коммит с первыми тестами должен предшествовать коммиту, где
заглушка `...` исчезла. На коммите с тестами реализация ещё должна быть
заглушкой, иначе это не TDD, а «всё сразу».

Если репозиторий склонирован с `--depth=1`, эта проверка предупреждает и
пропускается — история недоступна. Для полной проверки нужен обычный клон.

## Критерий готовности

```bash
$ ./scripts/check-part2.sh
  успех  Тесты расчёта заказа + покрытие >= 90%
  успех  Порядок TDD (тесты раньше кода)
```

Плюс зелёный `./scripts/check.sh` целиком: правила из части 1 продолжают
работать и для нового кода.

## Побочный эффект

Линтер в начале ругается на неиспользуемый импорт `validate_order` в тестах
(`F401`). Это исчезнет само, как только вы напишете тесты на валидацию.
